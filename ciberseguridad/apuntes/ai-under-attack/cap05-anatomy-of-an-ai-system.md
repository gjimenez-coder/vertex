## Capítulo 5 — Anatomy of an AI System (Anatomía de un sistema de IA)

> Nota de extracción: el texto se extrajo de la capa de texto del PDF; las citas indican la página del PDF.

## Lo que necesitas saber
Los sistemas de IA en producción no son solo modelos: son pilas (stacks) de data pipelines, prompts, sistemas de retrieval, capas de orquestación, APIs, llamadas a herramientas, infraestructura, monitoreo y flujos de trabajo humanos. El modelo es la parte visible, pero la postura real de seguridad surge de cómo se conectan todas esas piezas. El capítulo desmonta el sistema capa por capa para mostrar dónde vive cada componente y cómo cada capa genera su propia superficie de ataque.

La tesis central es que muchos equipos aseguran el endpoint del modelo y pasan por alto el camino de los datos de entrenamiento, revisan el prompt pero no la capa de retrieval, restringen la aplicación pero olvidan que el agente aún puede llamar a una herramienta con permisos permanentes (standing permissions). El límite de confianza (trust boundary) rara vez rodea solo al modelo: puede rodear una vector database, un feature store, un pipeline de logging, un plug-in, una cuenta de servicio o un paso de aprobación humana no documentado.

El objetivo no es memorizar diagramas de arquitectura, sino aprender a mirar un sistema de IA y hacer mejores preguntas de seguridad: qué datos lo formaron, qué contexto le llega, qué herramientas puede usar, qué puede cambiar y dónde debe aplicarse realmente el control. Sales sabiendo cómo mapear componentes, data flows, límites de confianza y la topología en tiempo de ejecución.

## El ejemplo que recorre el capítulo
El hilo conductor es el contraste entre el ML tradicional (p. ej. un sistema de detección de fraude o scoring crediticio: flujo lineal, determinista, acotado) y la IA generativa (entradas en lenguaje natural de variación infinita, salidas abiertas, múltiples integraciones). Reaparece el caso de un asistente/soporte al cliente basado en LLM que accede a vector databases, llama a APIs, ejecuta código en sandbox y mantiene memoria. El laboratorio cierra con NexaGuard, donde Ghost documenta la arquitectura completa antes de una auditoría, trazando una petición desde el API gateway hasta el filtrado de salida.

## De fundamentos clásicos a la complejidad generativa
El paso de ML tradicional a IA generativa cambió la forma de lo que hay que asegurar: el sistema completo, no solo el modelo.

- Blueprint de ML tradicional: ingesta por pipelines ETL (extract, transform, load), extracción de features con lógica predeterminada, entrenamiento batch sobre datos históricos etiquetados y salidas como clasificaciones binarias o scores de probabilidad. Flujo lineal y determinista; la seguridad se centraba en integridad de datos de entrenamiento, evitar model extraction y consistencia de predicciones.
- Transformación generativa: salidas abiertas (texto, código, datos estructurados), interpretación de lenguaje natural, y el mismo prompt puede dar respuestas distintas entre invocaciones, lo que dificulta la verificación de comportamiento. El entrenamiento pasa a pipelines multi-etapa (pretraining, supervised fine-tuning, reinforcement learning from human feedback), convirtiéndose en "una superficie de ataque multi-etapa en lugar de un único proceso a proteger" (PDF p. 145). Cada punto de integración multiplica la superficie de ataque.
- Herencia y divergencia: la IA generativa hereda pipelines MLOps, orquestación con Kubernetes y monitoreo del ML clásico, pero con desajustes: controles para sistemas deterministas aplicados a probabilísticos, access controls pensados para APIs estructuradas estirados a interfaces de lenguaje natural, y monitoreo estadístico que no detecta ataques semánticos. El resultado: frameworks de seguridad de ML que dan "false confidence" al aplicarse a IA generativa.

## El pipeline moderno de entrenamiento
### Preparación y curación de datos
La base es la data de entrenamiento, que puede alcanzar billones (trillions) de tokens. La infraestructura incluye web crawlers, sistemas de deduplicación que procesan petabytes, filtros de calidad y conversores de formato. La tokenización es un componente crítico pero tratado como paso utilitario, no como security boundary: es donde el texto crudo se convierte en tokens y donde pueden introducirse anomalías de codificación o secuencias envenenadas. Sistemas modernos usan tokenizers como `o200k_base` de OpenAI. Desajustes entre tokenización de entrenamiento e inferencia crean vulnerabilidades sutiles que pueden saltarse filtros. El tokenizer es "el primer lugar donde la entrada externa se encuentra con el modelo" (PDF p. 148).

La escala hace imposible la validación exhaustiva. Datasets abiertos: Dolma (3 billones de tokens), SlimPajama-627B y RefinedWeb. Mitigaciones: auditorías por muestreo estadístico, provenance tracking para linaje de datos, pipelines de deduplicación automatizada y clasificadores de contenido que marcan muestras dañinas o envenenadas. La cobertura total es impracticable, pero la parcial reduce riesgo. Infraestructura de apoyo: almacenamiento distribuido, clústeres Apache Spark, pipelines de filtrado y sistemas de metadatos de provenance.

### Proceso de entrenamiento multi-etapa
- Pretraining: donde ocurre la mayor parte del cómputo (semanas, cientos/miles de GPUs). Infra: clústeres con interconexión NVLink 5, frameworks como PyTorch FSDP (incl. FSDP2) y DeepSpeed ZeRO Stage-3, checkpointing periódico y monitoreo de curvas de pérdida. Un batch de datos envenenado al inicio de un run de varias semanas puede alterar el comportamiento del modelo solo bajo condiciones específicas en producción meses después.
- Supervised fine-tuning: adapta el modelo base con datasets curados más pequeños; define cómo responde a instrucciones y su "personalidad". Suele haber múltiples variantes, cada una con su linaje y postura de seguridad.
- Anotación humana: depende de contratistas externos o crowdsourcing, lo que introduce problemas propios. Alternativas más simples y económicas: Direct Preference Optimization (DPO) y Reinforcement Learning from AI Feedback (RLAIF).
- Fases adicionales: Constitutional AI (auto-crítica y revisión), retrieval-augmented training y tool-use training (que exige entornos sandboxed). El Capítulo 11 trata ataques a estas fases (data poisoning, inserción de backdoors).

### Dependencias de infraestructura
Cadena de dependencias que forma parte de la superficie de ataque: clústeres GPU (a menudo compartidos, requieren separación de jobs), frameworks (PyTorch, TensorFlow, JAX con CUDA, NCCL y cientos de paquetes Python), y el pipeline de artefactos del modelo (model registries, pipelines de validación, conversores y despliegue). Cada etapa es un punto potencial de inyección o manipulación. Las plataformas MLOps (MLflow, Kubeflow o servicios cloud-native) son la capa de control entre entrenamiento e inferencia, donde "una política mal configurada o un paso de revisión faltante" puede dejar llegar a producción un artefacto comprometido (PDF p. 152).

## Patrones de integración y sus vulnerabilidades
Cada punto de integración es un handoff, y los handoffs son donde se toman decisiones de confianza, a menudo implícitas.

### Patrón de API gateway
Expone capacidades gestionando autenticación, rate limiting y enrutamiento. Hereda del web tradicional pero falla con entradas de texto libre: el gateway puede verificar conteo de tokens y autenticación, pero no detecta de forma fiable un intento de prompt injection. Componentes: load balancers, servicios de autenticación, rate limiters (por peticiones y por consumo de tokens) y request routers. Gateways AI-aware (Cloudflare AI Gateway, GenAI gateway de Azure API Management) y la Responses API unificada de OpenAI. En despliegues multi-modelo, un gateway rutea entre modelos de contexto largo, de razonamiento, de otro proveedor y especializados, complicando el manejo de sesión y estado.

### Arquitectura RAG (retrieval-augmented generation)
Patrón dominante para fundamentar respuestas en información factual. Componentes: pipelines de ingesta de documentos (PDFs, páginas web, bases de datos), servicios de embedding (text-embedding-3-small/large de OpenAI, o BGE-M3, seleccionados vía el leaderboard MTEB), vector databases para búsqueda por similitud, servicios de retrieval que consultan y rankean, lógica de construcción de prompt, y el modelo que genera a partir del contexto aumentado. La integración con SharePoint, Confluence o Google Drive añade APIs, autenticación y formatos propios; los cambios upstream repercuten en el comportamiento de la IA. El Capítulo 8 cubre ataques específicos contra RAG; cada componente de la cadena de retrieval es parte de la superficie de ataque, no solo el modelo.

### Arquitecturas de agentes y uso de herramientas
Cuando los modelos pasan de responder a actuar, la anatomía cambia. La guía conjunta de ASD ACSC, CISA, NSA y socios enmarca los sistemas agénticos en torno a modelos, herramientas, datos externos, memoria, flujos de planificación y privilegios de ejecución. Patrones: ReAct (Reasoning and Acting), Plan-and-Execute. Frameworks de orquestación: LangChain, LlamaIndex, Semantic Kernel, DSPy, OpenAI Agents SDK y el Model Context Protocol (MCP). La ejecución de herramientas es compleja: cada una exige runtime, credenciales y acceso de red distintos; la ejecución de código requiere sandbox con límites de recursos (Firecracker microVMs, gVisor, Kata Containers).

### Memoria y gestión de estado
Capas de memoria de conversación: cachés de sesión (turnos recientes), bases de datos de conversación (historial completo), índices de embeddings (búsqueda semántica) y servicios de sincronización de estado. Problemas simultáneos: particionar estado entre usuarios para que no se filtre entre tenants, sincronizar entre servidores de inferencia, retirar conversaciones según retención y soportar recuperación exacta y semántica sin añadir latencia. La memoria a largo plazo (perfiles de usuario, knowledge graphs, bases de feedback) añade otra capa que asegurar.

### Frameworks de orquestación
La capa de orquestación es el "sistema nervioso": plantillas de prompt y contexto, definiciones de cadenas, gestores de memoria, selectores de herramientas y output parsers (que convierten texto en objetos tipados o JSON). Aquí el context engineering se vuelve control de seguridad: decidir qué instrucciones, chunks recuperados, memoria, resultados de herramientas y mensajes del usuario entran al contexto y en qué orden. A menudo contiene lógica de negocio crítica (reglas de escalado, checks de compliance). "Bugs de orquestación y reglas de enrutamiento mal configuradas han causado tantos problemas como fallas del modelo" (PDF p. 159).

## Capas de infraestructura y límites de seguridad
- Infraestructura de entrenamiento: redes aisladas con acceso restringido, cientos/miles de GPUs con interconexión de alta velocidad, filesystems distribuidos con petabytes, schedulers de jobs. Los runs duran semanas/meses, exponiéndolos a amenazas persistentes. El almacenamiento abarca object stores, filesystems distribuidos y arrays NVMe para checkpoints. Los checkpoints necesitan access controls e integrity verification: un checkpoint manipulado es casi indistinguible de uno limpio por inspección y puede extraer datos o alterar el comportamiento. La red optimiza ancho de banda interno (InfiniBand para gradient sync).
- Infraestructura de inferencia: moldeada por latencia y variabilidad, no por throughput; debe responder en cientos de milisegundos manteniendo aislamiento entre tenants. Suele correr en Kubernetes con auto-scaling, frameworks de serving como vLLM (PagedAttention), Text Generation Inference (TGI), TensorRT-LLM, o TorchServe/Triton, capas de caché y API gateways. Aislamiento multi-tenant: límites de contenedor con capacidades restringidas, virtualización de GPU con MIG, network policies y cuotas de recursos.
- Infraestructura de data pipelines: streaming (Kafka, Pulsar, Flink, Spark Streaming, schema registries), batch (Spark, Dataflow, Airflow, Prefect, validación y metadatos de linaje) e indexación vectorial para RAG (procesadores de documentos, embeddings acelerados por GPU, index builders, sincronización). Es donde afloran problemas de calidad, inyección y desajustes de formato.
- Arquitectura de red y segmentación: zonas DMZ (gateways externos), aplicación (orquestación, lógica de negocio), modelo (endpoints de inferencia con GPU), datos (vectores, conversaciones, documentos) y gestión (monitoreo, despliegue). Service mesh (Istio, Cilium) añade mTLS, políticas finas y observabilidad. La segmentación maneja aislamiento a nivel de infraestructura: necesario pero no suficiente, porque los límites más expuestos son los de confianza a nivel de aplicación.

## Límites de confianza e interfaces críticas
Los trust boundaries en IA son más difíciles de mapear: cruzan componentes de distintos equipos, runtimes y modelos de autenticación.

Boundaries primarios:
- Input/instruction boundary: recorre toda la pipeline, más allá del API. En RAG, el límite entre el modelo y el contenido recuperado es crítico: el modelo procesa el contenido como contexto pero no debe tratarlo como instrucciones. Si lo hiciera, un atacante que controle un documento del knowledge base podría inyectar comandos que anulen el system prompt o exfiltren datos: esto es indirect prompt injection. Es un límite arquitectónico (plantillas que delimitan el contenido recuperado, embedding models sin capacidad de seguir instrucciones, gestión cuidadosa del contexto).
- Límite modelo–herramientas: es un límite de seguridad real. Al invocar una tool, el agente cruza del entorno controlado a sistemas externos con efectos en el mundo real; debe aplicarse autenticación, autorización, validación de entrada y saneamiento de salida.
- Límite entre sesiones de usuario: asegura aislamiento multi-tenant en memoria de conversación, índices vectoriales, estado del modelo y cachés.

Límites temporales y de estado: cada turno añade al contexto que el modelo toma como verdad; el contexto previo puede estar comprometido. Hay que validar el contexto histórico, limitar cuánto influye, detectar manipulaciones y gestionar el overflow de la ventana de contexto. El límite entre sesiones decide qué persiste (preferencias) y qué no (tokens de autenticación temporales), con cifrado, control de recuperación y audit logs. Ejemplo: en un chatbot de soporte multi-turno, el límite entre turnos evita que el usuario en el turno tres referencie instrucciones inyectadas en el turno uno, y el límite entre sesiones evita que los datos personales de un cliente anterior sean visibles al siguiente.

Visualización y mapeo del sistema: inventarios de componentes, data-flow maps, trust-boundary maps, catálogos de integración, trazas de runtime e infrastructure as code (IaC) muestran cada uno un corte de la realidad. Juntos exponen la brecha entre diseño previsto y comportamiento en producción, clave en threat modeling e incident response.

## Ideas clave
- Un sistema de IA en producción no es un solo modelo tras una API, sino componentes interactuantes con sus propios failure modes: training pipelines, integraciones, infraestructura, data flows, trust boundaries y topología en runtime.
- El salto de ML tradicional a generativo amplió la superficie de ataque; heredar controles deterministas para sistemas probabilísticos da "false confidence".
- El pipeline de entrenamiento es multi-etapa (pretraining, fine-tuning, RLHF/DPO/RLAIF) y cada fase, más la tokenización, los datasets a escala de petabytes y MLOps, aporta puntos de inyección.
- Los API gateways no detectan prompt injection porque no interpretan texto libre; validan tokens y autenticación, no intención.
- En RAG, todo componente de la cadena de retrieval es superficie de ataque, y el contenido recuperado nunca debe tratarse como instrucción (indirect prompt injection).
- Los agentes cruzan a sistemas externos vía tools: ese límite exige autenticación, autorización, validación de entrada y saneamiento de salida.
- La orquestación concentra lógica de negocio y context engineering; sus bugs y reglas de enrutamiento mal configuradas causan tantos problemas como las fallas del modelo.
- Los trust boundaries clave (input/instruction, retrieval, tool, sesión/persistencia) son los lugares donde la aplicación del control ocurre o se omite; fallar uno abre camino a fuga de datos, manipulación o pivote a sistemas conectados.
