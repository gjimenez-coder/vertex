# Designing Data-Intensive Applications — Martin Kleppmann (O'Reilly Media, 2017)
## Capítulo 12 — The Future of Data Systems (El futuro de los sistemas de datos)

> Nota de extracción: el texto se obtuvo de la capa de texto del PDF; las citas usan la página del PDF como `(PDF p. N)`.

## Lo que necesitas saber

Este capítulo final abandona la descripción de "cómo son las cosas" para proponer cómo deberían diseñarse las aplicaciones de datos del futuro: robustas, correctas, evolucionables y, en última instancia, beneficiosas. Kleppmann escribe en primera persona porque son opiniones y especulaciones, pero recoge y ordena ideas de otros. La tesis central es que no existe una única herramienta que sirva para todos los casos de uso, así que las aplicaciones componen varias piezas de software; el reto es la integración de datos.

La propuesta es construir sistemas en torno al flujo de datos (dataflow): designar ciertos sistemas como sistemas de registro (systems of record) y derivar el resto mediante transformaciones asíncronas y débilmente acopladas sobre un log de eventos ordenado. Esto evita que un fallo en una parte se propague, facilita la evolución (reprocesar datos para rederivar vistas) y es la base de la idea de "desagregar" (unbundle) la base de datos en componentes componibles.

Sales sabiendo cómo integrar sistemas con CDC y event sourcing en lugar de transacciones distribuidas; cómo pensar los sistemas como un flujo entre write path y read path; cómo lograr corrección de extremo a extremo con identificadores de operación idempotentes y comprobación asíncrona de restricciones (coordination-avoiding); y por qué la verificación continua ("trust, but verify") importa. El capítulo cierra con una reflexión ética sobre analítica predictiva, sesgo, vigilancia y privacidad.

## Integración de datos (Data Integration)

Para cualquier problema existen varias soluciones con distintos compromisos (motores de almacenamiento log-structured, B-trees o columnar; replicación single-leader, multi-leader o leaderless). Todo software, incluso una base de datos "de propósito general", se diseña para un patrón de uso concreto. El primer reto es mapear producto a circunstancia; el segundo es que, en aplicaciones complejas, los datos se usan de muchas formas, así que se acaban combinando varias herramientas (OLTP + índice de búsqueda de texto completo, data warehouses, caches, ML, notificaciones).

Combinar herramientas especializadas derivando datos: cuando se mantienen copias de los mismos datos en varios sistemas, hay que tener claro dónde se escribe primero y qué representaciones derivan de qué fuentes. Una buena práctica es escribir primero en la base de datos de registro y capturar los cambios (change data capture, CDC) aplicándolos en el mismo orden al índice. Si todas las entradas pasan por un único sistema que decide un orden total de escrituras, es fácil derivar otras representaciones procesándolas en ese orden: es una aplicación del state machine replication / total order broadcast. Da igual usar CDC o un log de event sourcing: lo que importa es el principio de decidir un orden total. Actualizar un sistema derivado a partir de un log de eventos suele poder hacerse determinista e idempotente, lo que facilita recuperarse de fallos.

Datos derivados frente a transacciones distribuidas: a nivel abstracto logran lo mismo por medios distintos. Las transacciones distribuidas ordenan escrituras con bloqueos (2PL) y usan commit atómico para efecto exactamente-una-vez; CDC y event sourcing ordenan con un log y se basan en reintento determinista e idempotencia. La diferencia clave es que las transacciones suelen ofrecer linealizabilidad (y garantías como leer tus propias escrituras), mientras que los sistemas derivados se actualizan de forma asíncrona. Kleppmann considera que XA tiene mala tolerancia a fallos y rendimiento, por lo que, a falta de un buen protocolo de transacciones distribuidas ampliamente soportado, los datos derivados basados en log son el enfoque más prometedor para integrar sistemas. Aun así, no es productivo decir "la consistencia eventual es inevitable, apáñatelas" sin dar guías; más adelante se busca un término medio.

Los límites del orden total: en sistemas pequeños construir un log totalmente ordenado es factible (single-leader lo hace), pero al escalar surgen límites: si el throughput supera una máquina hay que particionar y el orden entre particiones es ambiguo; con varios datacenters hay un leader por datacenter y orden indefinido entre ellos; con microservicios sin estado compartido no hay orden definido entre servicios; y clientes con estado local u offline ven eventos en órdenes distintos. Formalmente, decidir un orden total es total order broadcast, equivalente a consenso; sigue siendo un problema de investigación abierto diseñar algoritmos de consenso que escalen más allá de un nodo y funcionen en entornos geográficamente distribuidos.

Ordenar eventos para capturar causalidad: cuando no hay enlace causal, ordenar eventos concurrentes de forma arbitraria no es problema; las actualizaciones del mismo objeto se ordenan enrutándolas a la misma partición. Pero las dependencias causales surgen de forma sutil (ejemplo: alguien elimina a su expareja de amigos y luego publica un mensaje; si amistad y mensajes se almacenan por separado, la notificación puede llegar en orden erróneo). No hay respuesta simple; puntos de partida: timestamps lógicos para dar orden total sin coordinación (aunque requieren manejar entregas desordenadas y metadatos extra); registrar un evento con el estado que vio el usuario y un identificador único al que referirse después; y algoritmos de resolución de conflictos (que no ayudan si hay efectos externos como enviar una notificación).

## Procesamiento batch y de streams

El objetivo de la integración de datos es que los datos acaben en la forma correcta en todos los lugares correctos; batch y stream processing son las herramientas. Sus salidas son datasets derivados (índices de búsqueda, vistas materializadas, recomendaciones, métricas agregadas). La diferencia fundamental es que el stream opera sobre datasets ilimitados y el batch sobre entradas de tamaño finito conocido, pero la distinción se difumina (Spark hace streaming con microbatches sobre un motor batch; Flink hace batch sobre un motor de streaming).

Mantener estado derivado: el batch tiene sabor funcional (funciones deterministas y puras, entradas inmutables, salidas append-only); el stream lo extiende con estado gestionado y tolerante a fallos. La asincronía es lo que hace robustos a los sistemas basados en logs: contiene fallos localmente, mientras que las transacciones distribuidas amplifican fallos al abortar si falla cualquier participante.

Reprocesar datos para la evolución de la aplicación: el stream refleja cambios con baja latencia; el batch permite reprocesar históricos para derivar nuevas vistas. Reprocesar permite reestructurar un dataset a un modelo completamente distinto. El ejemplo del cambio de ancho de vía ferroviario (gauge) en la Inglaterra del siglo XIX ilustra la migración gradual: se añade un tercer raíl (vía mixta) para que convivan ambos anchos y, al final, se retira el raíl antiguo. Las vistas derivadas permiten lo mismo: mantener esquema antiguo y nuevo en paralelo, migrar usuarios gradualmente y revertir si algo falla.

La arquitectura lambda propone registrar eventos inmutables en un dataset siempre creciente y derivar vistas con dos sistemas en paralelo: un batch (p. ej. Hadoop MapReduce) que produce una versión exacta y corregida, y un stream (p. ej. Storm) que produce una aproximación rápida. Fue influyente, pero tiene problemas prácticos: mantener la misma lógica en dos frameworks, fusionar las dos salidas (difícil con joins o sesionización) y el coste de reprocesar todo (lleva a batches incrementales que acaban complicándose como el stream). El trabajo más reciente unifica batch y stream en un mismo sistema: replay de eventos históricos por el mismo motor, semántica exactamente-una-vez y ventanas por tiempo de evento (no de procesamiento), como ofrece Apache Beam sobre Flink o Google Cloud Dataflow.

## Desagregar la base de datos (Unbundling Databases)

En abstracto, bases de datos, Hadoop y sistemas operativos hacen lo mismo: almacenar y procesar/consultar datos. Unix y las bases de datos relacionales abordaron la gestión de información con filosofías opuestas: Unix ofrece una abstracción fina sobre el hardware (pipes, ficheros, secuencias de bytes); las relacionales ofrecen una abstracción de alto nivel (SQL, transacciones) que oculta la complejidad. Kleppmann interpreta NoSQL como aplicar el enfoque Unix al OLTP distribuido, e intenta reconciliar ambas filosofías.

Componer tecnologías de almacenamiento: muchas features de las bases de datos (índices secundarios, vistas materializadas, logs de replicación, índices full-text) tienen paralelo en los sistemas derivados construidos con batch y stream. Ejecutar `CREATE INDEX` equivale a reprocesar el dataset y derivar un nuevo índice, igual que arrancar un follower o el snapshot inicial de un CDC. Visto así, el flujo de datos de toda una organización parece una gran base de datos ("meta-base de datos de todo"), donde batch, stream y ETL actúan como triggers, stored procedures y mantenimiento de vistas materializadas. Dos vías para componer herramientas: las bases de datos federadas (polystore) unifican lecturas con una interfaz de consulta común (p. ej. foreign data wrappers de PostgreSQL), siguiendo la tradición relacional; las bases de datos desagregadas (unbundled) unifican escrituras, sincronizando cambios entre sistemas dispares con CDC y logs de eventos, siguiendo la tradición Unix de herramientas pequeñas.

Para sincronizar escrituras, el enfoque tradicional de transacciones distribuidas entre tecnologías heterogéneas es, según el autor, la solución equivocada: un log ordenado de eventos con consumidores idempotentes es más simple y robusto. La integración basada en log aporta acoplamiento débil: a nivel de sistema, los streams asíncronos hacen al conjunto resistente a fallos de componentes individuales (el log amortigua mensajes); a nivel humano, permite que equipos distintos desarrollen y mantengan componentes de forma independiente con interfaces bien definidas.

Desagregado frente a integrado: el objetivo no es competir en rendimiento con una sola base de datos, sino cubrir un rango más amplio de cargas combinando varias ("amplitud, no profundidad"). Si una sola tecnología hace todo lo que necesitas, úsala. Falta todavía el equivalente al shell de Unix: un lenguaje de alto nivel y declarativo para componer sistemas (imaginar `mysql | elasticsearch` como el `CREATE INDEX` desagregado). Hay investigación temprana prometedora como el differential dataflow.

## Diseñar aplicaciones en torno al dataflow

Este enfoque de desagregar la base de datos se conoce como "database inside-out"; no es una arquitectura nueva sino un patrón de diseño, inspirado en lenguajes dataflow (Oz, Juttle), FRP (Elm) y lógica (Bloom). Incluso las hojas de cálculo tienen dataflow: al cambiar una celda, las fórmulas dependientes se recalculan solas. Eso es lo que queremos a nivel de sistema de datos: al cambiar un registro, que índices, caches y agregaciones derivadas se actualicen automáticamente, pero con tolerancia a fallos, escala y durabilidad.

El código de aplicación como función de derivación: un índice secundario, un índice full-text (detección de idioma, stemming, inverted index), un modelo de ML (derivado de los datos de entrenamiento) o una cache son datasets derivados mediante funciones de transformación. Cuando la función no es estándar (como `CREATE INDEX`), hace falta código a medida, y ahí las bases de datos flaquean (triggers y UDFs han sido un añadido tardío).

Separación de código de aplicación y estado: las bases de datos encajan mal como entorno de ejecución de código arbitrario (gestión de dependencias, versionado, upgrades). Herramientas como Mesos, YARN, Docker y Kubernetes hacen mejor esa única tarea. Hoy las apps web se despliegan como servicios sin estado y el estado va a la base de datos ("separation of Church and state"). La base de datos actúa como variable mutable compartida que se consulta por red, pero no permite suscribirse a cambios: hay que hacer polling (las suscripciones a cambios apenas empiezan a aparecer).

Dataflow: interacción entre cambios de estado y código. Pensar en dataflow renegocia la relación entre código y estado: el código responde a cambios de estado en un lugar provocando cambios en otro. Mantener datos derivados no es lo mismo que ejecución asíncrona de trabajos: el orden de los cambios importa (varias vistas deben procesar en el mismo orden) y la tolerancia a fallos es clave (perder un solo mensaje desincroniza el dataset derivado para siempre). Los stream processors modernos ofrecen orden estable y procesamiento fiable a escala, más baratos y robustos que las transacciones distribuidas.

Stream processors y servicios: componer operadores de stream se parece a los microservicios, pero el mecanismo es distinto: streams de mensajes asíncronos unidireccionales en vez de peticiones síncronas request/response. Ejemplo de conversión de divisa: en microservicios el código consulta un servicio de tipos de cambio; en dataflow se suscribe de antemano a un stream de actualizaciones y guarda el tipo en una base de datos local, de modo que al procesar la compra solo consulta localmente. Es más rápido y robusto (la petición de red más fiable es la que no se hace); en lugar de RPC tenemos un stream-table join entre compras y tipos de cambio, que es dependiente del tiempo (reprocesar requiere el tipo histórico).

## Observar estado derivado

Los sistemas dataflow crean y mantienen datasets derivados mediante el write path (precomputado y eager: al escribir, el dato atraviesa etapas hasta actualizar cada dataset derivado) y el read path (lazy: al llegar una petición se lee del dataset y se construye la respuesta). El dataset derivado es donde ambos caminos se encuentran: un compromiso entre trabajo en escritura y en lectura. Un índice full-text lo ilustra: sin índice, leer implica escanear como `grep` (poco trabajo al escribir, mucho al leer); precomputar todas las consultas es imposible (infinitas); una cache de las consultas comunes desplaza la frontera. Caches, índices y vistas materializadas simplemente desplazan esa frontera entre read path y write path. Es el mismo tema del ejemplo de Twitter del capítulo 1 (dibujar la frontera distinta para celebridades y usuarios normales): "tras 500 páginas cerramos el círculo".

Clientes con estado y capacidad offline: el modelo cliente/servidor (clientes sin estado, servidor con autoridad) se da por sentado, pero las single-page apps y las apps móviles mantienen estado local. Esto renueva el interés por aplicaciones offline-first que usan una base de datos local y sincronizan en segundo plano. El estado en el dispositivo puede verse como una cache del estado del servidor: los píxeles son una vista materializada de los objetos de modelo, que a su vez son una réplica local del estado remoto.

Empujar cambios de estado a los clientes: una web normal solo lee el estado una vez y queda obsoleta hasta recargar (RSS es polling básico). Server-sent events (EventSource) y WebSockets permiten al servidor empujar cambios activamente, extendiendo el write path hasta el usuario final. Si el dispositivo está offline, el mismo mecanismo de consumer offsets de un broker basado en log permite reconectar sin perder mensajes. Herramientas como Elm y React/Flux/Redux ya gestionan el estado del cliente suscribiéndose a un stream de eventos (similar a event sourcing); extenderlo end-to-end permitiría propagar cambios con baja latencia (bajo un segundo). El reto es que request/response está muy arraigado; habría que moverse hacia publish/subscribe.

Las lecturas también son eventos: además de escribir vía log, se pueden representar las lecturas como streams de eventos y enrutarlas al mismo operador, convirtiendo la consulta en un stream-table join entre el stream de consultas y la base de datos. Una lectura puntual pasa por el join y se olvida; una suscripción es un join persistente con eventos pasados y futuros. Registrar un log de lecturas ayuda a rastrear dependencias causales y procedencia (reconstruir qué vio el usuario antes de decidir), a costa de almacenamiento e I/O extra.

Procesamiento multi-partición: enviar consultas por un stream es excesivo para una sola partición, pero abre la puerta a ejecución distribuida de consultas complejas que combinan varias particiones (distributed RPC de Storm; prevención de fraude combinando varias bases de reputación particionadas). Para joins multi-partición suele ser más simple usar una base de datos que lo ofrezca, pero tratar consultas como streams da una opción cuando se superan los límites de soluciones convencionales.

## Buscar la corrección (Aiming for Correctness)

Los sistemas con estado recuerdan "para siempre", así que los errores también duran: requieren más cuidado. Durante cuatro décadas, atomicidad, aislamiento y durabilidad (ACID) han sido las herramientas, pero son más débiles de lo que parecen (confusión de niveles de aislamiento débiles; los experimentos Jepsen de Kyle Kingsbury revelan discrepancias entre garantías prometidas y comportamiento real ante fallos de red). Serializabilidad y commit atómico funcionan, pero suelen limitarse a un solo datacenter y limitan escala y tolerancia a fallos.

El argumento end-to-end para bases de datos: usar transacciones serializables no garantiza ausencia de pérdida o corrupción; un bug de la aplicación puede escribir o borrar datos mal. La ejecución exactamente-una-vez evita corrupción por procesar dos veces (cobrar doble, incrementar un contador dos veces); se logra sobre todo haciendo la operación idempotente, lo que exige metadatos (IDs de operación) y fencing al hacer failover. La supresión de duplicados de TCP solo vale dentro de una conexión; si el cliente reintenta tras un timeout, la transacción (Ejemplo 12-1, transferencia no idempotente) puede ejecutarse dos veces. Ni TCP, ni las transacciones, ni los stream processors bastan por sí solos. La solución es end-to-end: un identificador de operación (p. ej. UUID) generado por el cliente y propagado hasta la base de datos, con una restricción de unicidad sobre `request_id` (Ejemplo 12-2) que suprime duplicados. Esto ilustra el argumento end-to-end de Saltzer, Reed y Clark (1984): la función solo puede implementarse de forma completa con el conocimiento de los extremos. Aplica también a integridad (checksums end-to-end) y cifrado (solo el cifrado end-to-end protege de todo). Las features de bajo nivel siguen siendo útiles porque reducen la probabilidad de problemas, pero no bastan.

Imponer restricciones: la unicidad (usernames, emails, un asiento por persona) y restricciones similares (saldo no negativo, no vender más stock del disponible) requieren consenso en un entorno distribuido. Lo habitual es un único leader; la replicación multi-master asíncrona queda descartada porque podría aceptar escrituras conflictivas. La comprobación de unicidad se escala particionando por el valor que debe ser único. En mensajería basada en log, un stream processor consume secuencialmente una partición (log = total order broadcast = consenso) y decide de forma determinista qué operación conflictiva ganó, emitiendo éxito o rechazo a un stream de salida. Procesamiento multi-partición: una transferencia que toca tres particiones (request ID, cuenta origen, cuenta destino) puede lograr la misma corrección sin commit atómico: se registra la petición como un único mensaje (atómico) y de él se derivan instrucciones de débito y crédito, deduplicando por request ID; aunque el procesador reintente tras un fallo, al ser determinista produce las mismas instrucciones.

Puntualidad e integridad: "consistency" mezcla dos requisitos distintos. La puntualidad (timeliness) asegura ver el estado actualizado; su violación es consistencia eventual, temporal y resoluble esperando (linealizabilidad es una forma fuerte de lograrla). La integridad es ausencia de corrupción (sin pérdida ni datos contradictorios); su violación es "inconsistencia perpetua" y requiere comprobación y reparación explícitas. En la mayoría de aplicaciones la integridad importa más (un retraso en el extracto bancario es tolerable; que los saldos no cuadren es catastrófico). Los sistemas dataflow basados en eventos desacoplan puntualidad e integridad: la semántica exactamente-una-vez, la entrega fiable, la supresión de duplicados con request ID end-to-end y la inmutabilidad de eventos preservan integridad sin transacciones distribuidas.

Restricciones laxas y sistemas que evitan coordinación: muchas aplicaciones toleran violar temporalmente una restricción y corregirla con una transacción compensatoria o una disculpa (pedir a uno de dos usuarios que elija otro username, reponer stock y ofrecer descuento, overbooking de aerolíneas y hoteles, cobrar comisión por descubierto). Si el coste de la disculpa es aceptable, no hace falta una restricción linealizable: se puede escribir optimistamente y comprobar después. Estas apps necesitan integridad, no puntualidad en la restricción. Así, los sistemas que evitan coordinación mantienen integridad sin commit atómico ni coordinación síncrona, pudiendo operar multi-datacenter en multi-leader; la coordinación síncrona se introduce solo donde es imprescindible. Coordinación y restricciones reducen las disculpas por inconsistencia pero aumentan las disculpas por indisponibilidad: hay que buscar el punto óptimo.

Confía, pero verifica (Trust, but Verify): los modelos de sistema asumen que ciertas cosas fallan y otras no, pero en realidad es cuestión de probabilidades. Los datos pueden corromperse en disco o en red (eludiendo checksums de TCP); existen bit-flips aleatorios y ataques como rowhammer; hay bugs incluso en MySQL y PostgreSQL (unicidad mal mantenida, write skew bajo aislamiento serializable). La corrupción es inevitable a la larga, así que hay que auditar: comprobar la integridad de los datos. Sistemas como HDFS y S3 no confían ciegamente en los discos: leen en segundo plano y comparan réplicas. Conviene restaurar backups periódicamente. Los sistemas basados en eventos facilitan la auditabilidad (diseñar para auditabilidad): la entrada es un evento inmutable, la derivación es determinista y repetible, se usan hashes para el log y se puede rederivar para verificar. Herramientas criptográficas como árboles de Merkle (usados en certificate transparency) podrían generalizarse para auditoría; el autor es escéptico con la tolerancia a fallos bizantinos y el proof of work, pero valora el chequeo de integridad.

## Hacer lo correcto (Doing the Right Thing)

Todo sistema se construye con un propósito y toda acción tiene consecuencias intencionadas y no intencionadas; los ingenieros tienen la responsabilidad de considerarlas. Muchos datasets son sobre personas y deben tratarse con humanidad y respeto. Existen guías como el código de ética de la ACM, pero rara vez se aplican.

Analítica predictiva: predecir el clima es distinto de predecir si un condenado reincidirá, si alguien impagará un préstamo o hará reclamaciones caras: estas decisiones afectan directamente a la vida de las personas. Quien sea etiquetado como "de riesgo" puede sufrir una cadena de "noes" (exclusión de empleo, viajes, seguros), lo que se ha llamado "prisión algorítmica", sin presunción de inocencia ni apelación. Sesgo y discriminación: un algoritmo no es mejor ni peor que un humano, pero si la entrada tiene sesgo sistemático, el sistema lo aprende y amplifica; rasgos aparentemente neutros (código postal, IP) pueden correlacionar con rasgos protegidos (raza). La analítica predictiva extrapola del pasado; si el pasado es discriminatorio, codifica la discriminación ("machine learning is like money laundering for bias"). Responsabilidad y rendición de cuentas: ¿quién responde cuando el algoritmo se equivoca? Un credit score resume "cómo te comportaste", mientras la analítica predictiva opera sobre "quién se parece a ti", lo que implica estereotipar. Los datos son estadísticos: incluso con una distribución correcta, los casos individuales pueden estar mal. Bucles de retroalimentación: los sistemas que predicen qué quiere ver el usuario crean cámaras de eco; usar el credit score para contratar puede generar espirales descendentes. El systems thinking ayuda a prever estas consecuencias. Los datos y modelos deben ser herramientas, no amos.

Privacidad y rastreo: cuando el sistema solo guarda lo que el usuario introduce, le presta un servicio; cuando rastrea su actividad como efecto colateral, la relación cambia. El rastreo conductual mejora búsquedas y recomendaciones, pero si el servicio se financia con publicidad, los clientes reales son los anunciantes y el rastreo deriva en vigilancia (surveillance). Kleppmann propone sustituir "data" por "surveillance" para notar cuánto hemos construido la mayor infraestructura de vigilancia de la historia, con un Internet de las Cosas lleno de micrófonos. Consentimiento y libertad de elección: los usuarios no entienden qué datos ceden ni cómo se procesan, así que no hay consentimiento significativo; además, los datos de un usuario hablan de otros. La relación es asimétrica, y no usar un servicio de facto obligatorio no es libertad real. Privacidad no es secreto total, sino el derecho a decidir qué revelar y a quién; con la vigilancia, ese derecho se transfiere del individuo a la empresa. Datos como activo y poder: los datos conductuales ("data exhaust") son en realidad el activo central; existen data brokers y los datos se filtran con frecuencia, por lo que se habla de "activo tóxico" o "material peligroso". Al recopilar hay que sopesar beneficios frente al riesgo de que caigan en malas manos, considerando todos los gobiernos futuros posibles. Recordando la Revolución Industrial: igual que aquella trajo progreso y también contaminación y abusos que necesitaron regulación, la era de la información necesita confrontar el problema de los datos ("los datos son el problema de contaminación de la era de la información", Schneier). Legislación y autorregulación: leyes como la Directiva Europea de Protección de Datos de 1995 chocan con la filosofía Big Data de maximizar la recolección. Hace falta un cambio cultural: tratar a los usuarios como humanos con dignidad y agencia, autorregularse, no retener datos para siempre y explorar control de acceso mediante protocolos criptográficos en lugar de solo políticas. La vigilancia ubicua no es inevitable.

## Ideas clave

- No hay una sola herramienta para todos los casos de uso: las aplicaciones componen varios sistemas y el reto es la integración de datos.
- Integrar con CDC y logs de eventos (datos derivados asíncronos) es más robusto y práctico que las transacciones distribuidas (XA), aunque sacrifica linealizabilidad por defecto.
- Decidir un orden total de escrituras (total order broadcast, equivalente a consenso) facilita derivar vistas; escalarlo más allá de un nodo o entre datacenters sigue siendo un problema abierto.
- Batch y stream comparten principios (funciones deterministas, idempotencia); reprocesar datos permite evolucionar esquemas y migrar gradualmente de forma reversible.
- "Desagregar" la base de datos: componer almacenamiento y procesamiento especializados (federación para lecturas, unbundling con logs para escrituras) buscando amplitud de cargas, no profundidad.
- Diseñar en torno a dataflow: el código responde a cambios de estado; caches, índices y vistas materializadas solo desplazan la frontera entre write path y read path, que puede extenderse hasta el cliente (offline-first, publish/subscribe).
- La corrección exige medidas end-to-end (identificadores de operación idempotentes); conviene separar puntualidad (consistencia eventual, temporal) de integridad (inconsistencia perpetua), siendo la integridad lo más importante.
- Los sistemas que evitan coordinación mantienen integridad sin commit atómico; muchas apps toleran restricciones laxas corregidas con compensaciones. Y hay que auditar continuamente ("trust, but verify"), además de asumir la responsabilidad ética sobre analítica predictiva, sesgo, vigilancia y privacidad.
